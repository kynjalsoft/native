# ZyndMail native preview mail alerts

The Bulwark-based ZyndMail preview is a separate signed app, `io.zyndpay.mail.preview`, in Expo project `654a0262-9785-4753-8f37-9b0947b537a2`. Its company OAuth client is `zyndmail-native-preview`, and both staff and generic sign-in callbacks use the preview-only `zyndmailpreview` URL scheme. It must not reuse Bulwark's callback scheme or the installed ZyndMail app's push credentials, application ID, or production update channel. Generic providers must accept this distinct callback before their sign-in paths can be qualified.

Company mail alerts use the authenticated ZyndPay mail-plane relay in `kynjalsoft/zyndpay` PR #2585. The app sends its Expo push token only to the configured `EXPO_PUBLIC_MAIL_PUSH_RELAY_ORIGIN` HTTPS origin. Without that value, company push is visibly unavailable and no device registration is attempted. Public Bulwark accounts retain their existing Android FCM relay, but the company account never registers with it. Android uses one native Firebase service to route Bulwark data messages to the existing headless task and other messages to Expo Notifications.

The production relay advertises `previewMode: "sender-subject-snippet-v1"` for opted-in previews. When `/v1/push-health` also advertises `routingVersion: 2`, the client requests that version on registration, and the relay includes `registrationId` in Expo data alongside `version` and opaque `notificationRef`. Without that advertisement, the client uses the existing registration contract and treats rich foreground payloads without a registration ID as generic. Existing signed v1 clients retain their original payload. Historical references without a message identity cannot open a specific email; the client rejects them and explains that the link could not be verified instead of opening All Inboxes. Preview-specific relay configuration and signed-device behavior still require qualification. Visible preview text passes through Expo and the platform push provider. A provider ticket, receipt, app foreground handler, and physical OS presentation are separate evidence.

In the foreground, a rich relay alert is shown only when its registration ID matches the active, preview-enabled staff registration and local session identity. Tapping still resolves the opaque reference against the relay and JMAP before opening the exact authorized email. Older rich payloads without a registration ID produce a generic local alert with the same reference. Payloads with an explicit mismatched registration ID are suppressed without a tap target. The foreground handler does not display their unverified sender, subject, or snippet.

Background and terminated notifications can be displayed by iOS or Android before JavaScript checks registration ownership. The relay sends rich content only for opted-in preview registrations, and the app requests revocation and dismisses presented cards on switch, logout, or preview opt-out. A rich payload already handed to Expo, APNs, or FCM can still appear after that change; neither client dismissal nor relay revocation can recall it. Qualify this in-flight window on both signed physical devices, including lock-screen behavior.

The preview cannot be called notification-ready until all of these are witnessed:

1. Configure the preview OAuth client and redirect URI in Keycloak, and confirm a signed preview build can authenticate and read the current JMAP session. Do not treat simulator or anonymous endpoint reachability as staff acceptance.
2. Qualify the separate Firebase Android app for `io.zyndpay.mail.preview` and a company-owned APNs identity for the iOS preview. Firebase project `zyndmail-native-preview` and its Android app are registered. Its `google-services.json` is held as the preview-only EAS `GOOGLE_SERVICES_JSON` secret file; the EAS pre-install hook checks the exact project and package before copying it into the ignored native path. FCM v1 server credentials, a signed build, and actual delivery remain unverified. Keep `google-services.json` out of Git and verify the merged Android manifest has exactly one `com.google.firebase.MESSAGING_EVENT` service.
3. Qualify PR #2585 against live Stalwart's callback and subscription semantics, then deploy the relay and configure its optional preview OAuth-client/EAS-project/app-ID tuple. Keep the tuple unset until that qualification passes.
4. Configure the reviewed HTTPS relay origin in the preview build and prove registration, foreground/background/terminated alerts and taps on signed physical iOS and Android devices. Exercise shared-account mail, access revocation, logout, account switch, token rotation, relay outage, and lease renewal without sending mail to unrelated recipients.
5. Inspect relay/provider logs for unintended mail content and confirm opted-in preview payloads contain only the bounded sender, subject, and safe snippet. Keep production company push disabled if any identity, permission, or callback gate fails.

The relay origin in `eas.json` is build-time configuration, not release activation. Do not create or distribute a production-profile signed release build, publish a production update, or submit to a store until signed iOS and Android physical-device preview and exact-tap qualification is recorded. Internal signed qualification builds are for those tests only.

The preview is configured for its own EAS Update project and `preview` channel. `eas update:configure` configured the committed Android project; `app.config.js` supplies the dynamic config and generated iOS project. Generated `Expo.plist` contains the preview request header, URL, and runtime. Android's committed manifest carries the same URL and channel. The initial runtime is iOS app version `0.1.62` and Android `1.0.0`. Bump the Android runtime whenever native code or native dependencies change; bump `VERSION` for an incompatible iOS native build. An update must match the installed platform, runtime, and channel. The existing GitHub-hosted iOS/Android release workflows and EAS preview profile all target this preview channel; they do not target the installed first-party ZyndMail app.

`testflight-preview` is the store-signed iOS build profile for internal TestFlight qualification of this separate preview identifier. It uses the same isolated preview EAS environment and update channel; it is not a public App Store submission profile. The Android `preview` profile produces the separate internal APK. Never submit either candidate as the existing `io.zyndpay.mail` app or claim the TestFlight build is usable until App Store Connect processing and the intended internal tester's install are verified.

An isolated, harmless OTA from commit `c401a0a` was published only to this project's `preview` channel: iOS update `01a0d3b7-f59b-793f-ac61-f5fbca5a0c21` for runtime `0.1.62`, and Android update `01a0d3b7-f59b-7787-8448-da7c72812042` for runtime `1.0.0`. A locally compiled, unsigned iOS Release simulator app downloaded the exact iOS update on one cold launch; the Expo Updates database recorded one successful launch of that update on the next, and the sign-in screen remained usable. This verifies preview transport on a simulator, not a signed build, physical-device delivery, or the Android update. Normal release builds download a compatible update in the background on launch. The preview checks again when foregrounded, at most once per 15 minutes, and applies a downloaded update automatically on the idle, authenticated Mail tab. It defers while a draft, message, account flow, outbox replay, or undo-send action is active. Signed-device acceptance of the automatic reload remains open.
